# AdjointRWM Production Training Evaluation and Directed Next Steps

## Executive verdict

**Classification:** `PIPELINE_SMOKE_TEST_PASSED / PRODUCTION_MODEL_TRAINING_NOT_ESTABLISHED`

The archive is technically readable, the checkpoint loads safely, all stored tensors are finite, and every dataset file matches the SHA-256 value recorded in its manifest. However, the run does not establish a useful real-data embodied world model.

The decisive issue is the dataset. The 20 files labelled as a DROID subset contain 600 deterministic pseudo-random state/action rows rather than real DROID observations. Across all episodes, the exact data can be regenerated by one NumPy stream initialized with `np.random.seed(42)`, followed at every step by:

```python
action = np.random.uniform(-1, 1, 7)
state = np.random.uniform(-2, 2, 10)
```

The archive contains only image hash strings, not exterior or wrist image payloads. States and actions are independent random draws, with essentially zero lag-one temporal correlation. Consequently, the model has not learned real robot dynamics, visual prediction, action-conditioned physical transitions, or useful co-state allocation.

The checkpoint should be preserved as a **software-path smoke-test artifact**, but it should not be promoted, deployed, compared against the research teacher, or used as a production warm start.

## Inferred checkpoint architecture

The stored state dictionary is consistent with a state/action-only pilot:

- state adapter: `10 -> 512`;
- action adapter: `7 -> 512`;
- feature projection: `1024 -> 1024`;
- three-layer GRU with hidden width `1024`;
- coarse-to-fine residual MLP;
- future predictor: `1024 -> 1024`;
- co-state head: `1024 -> 512`;
- direct critic head: `1024 -> 1`;
- selective gate head: `1024 -> 128 -> 1`;
- teacher projection: `1024 -> 512`.

The parameter count is within the intended L4 pilot envelope. The architecture itself is a usable starting design, but its current weights are not useful because the data have no physical temporal structure and the selective gate and teacher projection were not trained.

## Directed next phases

### Phase R0 — Real-data and provenance reset

Acquire an actual bounded DROID shard through the publisher-supported schema or loader. A valid episode must include:

- original dataset/version and episode identifier;
- actual exterior and wrist image frames or verified paths to them;
- robot state and action arrays;
- timestamps with alignment checks;
- language/task metadata when available;
- scene, task, site, and embodiment metadata when available;
- source URL or dataset object identifier;
- verified license text and attribution requirements;
- SHA-256 hashes of downloaded shards and derived episode indexes.

Use 20–100 real episodes for the first smoke test. Abort if any required observation is replaced by a hash-only placeholder or pseudo-random surrogate.

### Phase R1 — Reproducible real-data smoke run

Run 100–200 optimizer steps on real trajectories in BF16 autocast on the L4. The run must:

- split by entire trajectory before windows are generated;
- decode and display at least eight episodes;
- verify image/state/action timestamp alignment;
- run all heads, including gate and teacher projection;
- assert nonzero finite gradients for every intended trainable module;
- save train and validation metrics every evaluation interval;
- perform a forced interruption and deterministic resume;
- reload the final checkpoint in a clean model instance.

The checkpoint schema must include model, critic, optimizer, scheduler, scaler, sampler, RNG states, run ID, epoch, global step, data/config/source hashes, and best metrics.

### Phase R2 — Real pilot on 500–1,000 episodes

Train the state/action/visual temporal model and evaluate:

- one-step state prediction in native units;
- multi-step rollout error by horizon;
- image/latent future prediction;
- persistence and linear-dynamics baselines;
- latent variance and effective rank;
- held-out task/scene/site performance;
- uncertainty calibration;
- throughput, VRAM, dataloader wait, and checkpoint cost.

No adjoint-superiority claim opens until the dynamics model beats simple baselines on held-out trajectories.

### Phase R3 — Co-state, critic, and allocation confirmation

Generate valid teacher labels only for states/objectives where the teacher interface is defined. Train and compare:

- direct critic;
- directional-only allocator;
- full co-state allocator;
- randomized co-state control;
- wrong-goal and wrong-horizon controls;
- fixed allocation;
- full-compute allocation.

Primary allocator endpoints are candidate ranking and allocation regret/AURC, not training loss or mean allocation magnitude. Confirm that the selective gate and teacher projection have optimizer state and measurable held-out value.

### Phase R4 — L4 specialist production run

Promote to 2,000–5,000 stratified real episodes only when R2 and R3 pass. Preserve a 20–60M parameter envelope initially. Use:

- BF16 autocast;
- FP32 optimizer states and sensitive reductions;
- AdamW with warmup and a validated decay schedule;
- gradient clipping;
- measured microbatch sweep over `8, 16, 32, 64`;
- gradient accumulation where useful;
- early stopping on held-out dynamics, allocation, calibration, and planning gates.

### Phase R5 — Hardware promotion decision

Stay on L4 unless measured evidence shows one of the following:

- the minimum useful image/context/camera workload does not fit after BF16 and sensible checkpointing;
- L4 wall-clock time makes the promoted run operationally impractical;
- profiling shows a material memory-bandwidth or compute bottleneck;
- larger context, resolution, camera count, or model capacity produces a demonstrated held-out gain;
- frequent full imagined-adjoint sweeps dominate runtime.

Dataset size or unused VRAM alone is not an A100 trigger.
